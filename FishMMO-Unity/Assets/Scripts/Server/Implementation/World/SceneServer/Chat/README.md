# Chat System

## Overview

The Chat system is the SceneServer authority for player messaging across world, region, say, party, guild, tell, trade, system, and Discord channels. It validates inbound client chat, enforces rate/spam limits, routes channel-specific broadcasts, and persists eligible messages through asynchronous database operations.

The implementation is split into:
- Main-thread game/network execution for validation and broadcasting.
- Async worker execution for database fetch/persist work.
- A dedicated main-thread queue data container for marshaling async results back to safe broadcast context.

## Core Contracts

Related interfaces:
- `IChatSystem`
- `IChatSystemRuntimeData`
- `IChatSystemMainThreadQueueData`

- `ChatSystemRuntimeData`
- `ChatSystemMainThreadQueueData`
- `AsyncWorkerData`

## Initialization and Lifecycle

`InitializeOnce()`:
1. Validates required dependencies and data containers.
2. Initializes chat command routing via `ChatHelper.InitializeOnce(GetChannelCommand)`.
3. Registers `ChatBroadcast` network handler.
4. Registers periodic callback for chat message pumping.

`OnDeinitialize()`:
1. Drains pending main-thread queue actions.
2. Unregisters network handler.
3. Unregisters periodic callback.

## Message Intake Pipeline

Inbound client messages are handled by `OnServerChatBroadcastReceived(...)` and `ProcessNewChatMessage(...)`.

Validation and normalization stages:
1. Connection/object/sender validation.
2. Length and null/whitespace validation.
3. Rate limiting via `NextChatMessageTime`.
4. Repeat-message filtering (when repeat suppression is enabled).
5. Text sanitization (`ChatHelper.Sanitize`).
6. Command extraction (`ChatHelper.GetCommandAndTrim`).
7. Command routing using chat command registry.

If a channel handler returns `true`, the message is eligible for persistence.

## Channel Routing Model

### Synchronous channels
- **World**: broadcast to all mapped characters in world.
- **Trade**: broadcast to all mapped characters in world.
- **Region**: broadcast to all connections in sender scene.
- **Say**: broadcast to sender observers.

### Async membership channels
- **Party**: fetch party membership asynchronously, marshal broadcast to main thread, persist on success.
- **Guild**: fetch guild membership asynchronously, marshal broadcast to main thread, persist on success.
- **Tell**: resolve target asynchronously, marshal relay/status responses to main thread, persist on success.

### Server-origin channels
- **System**: direct server-to-client notifications.
- **Discord**: world-scoped relay to connected characters.

## Database Pump

A periodic message pump (`OnPeriodicMessagePump`) dispatches async fetch work:
1. Fetches new chat records after `LastFetchTime` and `LastFetchPosition`.
2. Enqueues main-thread application of fetched messages.
3. Updates cursor state in `IChatSystemRuntimeData` on main thread.

This allows multi-source chat propagation while preserving thread safety for network broadcasts.

## Runtime Data Containers

### `ChatSystemRuntimeData`
Holds poll cursor state:
- `LastFetchTime`
- `LastFetchPosition`

Both are reset during initialize/clear/deinitialize.

### `ChatSystemMainThreadQueueData`
Per-system queue for main-thread actions generated by async tasks.
Used to safely execute broadcast work in `OnLateUpdate()` and during deinitialize draining.

## Async Worker and Backpressure

All async DB operations are dispatched through `TryEnqueueAsyncWork(...)`:
- Returns `true` when accepted.
- Returns `false` when queue is unavailable or full.
- Logs warnings on rejection/unavailability.
- Supports `entityKey` ordering for per-character chat operations.

This protects server responsiveness by preventing unbounded fire-and-forget task growth.

## Failure Semantics

- Invalid chat input is dropped; exploit-like payloads can trigger kicks.
- Missing dependencies or failed async fetches exit safely.
- Queue backpressure is logged and work is skipped rather than blocking the main thread.
- Only successful, eligible channel flows are persisted.
